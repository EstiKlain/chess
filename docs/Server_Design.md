# Server Design — משחק מקוון בקנה מידה גדול

מסמך זה מציג הצעת ארכיטקטורה לצד השרת, בהתאם לדרישות ה-Scale: תמיכה ב-100 מיליון משתמשים רשומים, 10 מיליון משתמשים פעילים בו-זמנית, משחקים קצרים (30–90 שניות) עם קצב עדכון של צעד כל 2 שניות.

---

## 1. אפיון השרתים ומסד הנתונים

### מסד נתונים

**SQLite כמסד נתונים:**
- SQLite הוא מסד נתונים מבוסס קובץ בודד — אין תמיכה טבעית בגישה מבוזרת ממספר שרתים/תהליכים במקביל.
- כתיבות ננעלות ברמת הקובץ כולו (Locking) — צוואר בקבוק תחת עומס כתיבה מקבילי.
- אין replication מובנה, אין sharding — לא ניתן לפזר נתונים בין מספר מכונות.
- נבנה לשימוש מקומי/embedded, לא לשירות שרת בקנה מידה גדול. ברגע שיש כמה Docker-ים במקביל, כל אחד יראה עותק נפרד של הנתונים — ללא מקור אמת משותף.

**מה כן מתאים — הפרדה לפי סוג הנתון:**
- **נתונים קבועים** (פרופיל, סטטיסטיקות, רכישות, היסטוריה): מסד יחסי מבוזר — PostgreSQL עם Read Replicas, ואפשרות ל-Sharding לפי `user_id` בעתיד (Aurora/CockroachDB/Spanner כאופציות מנוהלות).
- **מצב זמן-אמת** (מי מחובר עכשיו, מי נמצא באיזה חדר): מסד מפתח-ערך מהיר כמו **Redis** — לא מסד יחסי, כי זהו מידע חולף שדורש throughput וקריאה/כתיבה מהירים, לא persistency כבד לטווח ארוך.

**מבחינת נפח בלבד:** 100 מיליון משתמשים רשומים הם בעיקר עניין של *אחסון* (סדר גודל של עשרות GB) ולא *עומס בו-זמני* — DB יחסי אחד מאונדקס נכון מכיל זאת בקלות. האתגר האמיתי הוא 10 מיליון המשתמשים הפעילים בו-זמנית, וזה מטופל דרך ריבוי Game Servers ולא דרך ה-DB.

### שרתי המערכת

| רכיב | תפקיד | אופי |
|---|---|---|
| **Gateway / Load Balancer** | נקודת כניסה יחידה ללקוחות; מנתב חיבורים | Stateless, ארוך-חי |
| **Auth Server** | הרשמה, התחברות, ניהול משתמשים, הנפקת טוקנים | Stateless (למעט DB) |
| **Matchmaking / Lobby Service** | משייך שחקנים לחדרים; לא מריץ את המשחק בעצמו | Stateless, ארוך-חי |
| **Presence / Registry (Redis)** | מיפוי בזמן אמת: איזה חדר רץ על איזה שרת/Pod | מסד מפתח-ערך |
| **Game Server Instances** | מריצים את לוגיקת המשחק בפועל; כל אחד מארח חדרים רבים במקביל | Stateful (לחדר עצמו), קצר-חי |
| **DB Server (PostgreSQL, Master + Replicas)** | מקור אמת יחיד לנתונים קבועים | Stateful |

**עקרון מפתח:** כל *חדר (Room)* בודד חי במלואו על Docker אחד בזמן נתון — כדי לא לסבך סנכרון בין תהליכים על אותה סימולציה. מה שגדל דינמית עם העומס הוא *מספר החדרים* ו*מספר ה-Docker-ים*, לא מספר ה-Container-ים לכל משחק בודד (ראו הסבר בסעיף 4).

## 2. תקשורת בין שרתים

**עיקרון מנחה: הבחירה בפרוטוקול תלויה בדפוס התקשורת, לא רק ב"מה יותר מהיר":**

| קשר | פרוטוקול | למה |
|---|---|---|
| Client ↔ Game Server | **WebSocket** (או UDP) | תדירות גבוהה (כל 2 שניות), חיבור "חי" למשך כל המשחק, דורש push דו-כיווני מהשרת ללקוח — לא רק בקשה-תשובה |
| Matchmaking ↔ Game Server | **REST / gRPC** | תקשורת מנהלתית ("יש לי מקום לחדר נוסף?") בתדירות נמוכה משמעותית מתעבורת השחקנים. gRPC (בינארי, מעל HTTP/2) כבר נותן מהירות בלי המורכבות של ניהול חיבורי WebSocket פתוחים לכל שירות-שירות |
| שירותי Backend ↔ DB | פרוטוקול DB רגיל (libpq וכו') | רק שרתי Backend מתחברים ישירות ל-DB, לעולם לא ה-Client |
| Presence/Registry | Redis protocol | קריאה/כתיבה מהירה של מיפוי חדר → שרת |
| גילוי שירותים (Service Discovery) | מנגנון פנימי של Kubernetes/K3s | Gateway צריך לדעת אילו Pods חיים כרגע ומה כתובתם — K8s מתחזק זאת אוטומטית |

**זרימה טיפוסית:** שחקן מתחבר ל-Gateway → מתאמת מול Auth → פונה ל-Matchmaking לבקש/ליצור חדר → Matchmaking שואל את ה-Registry (Redis) על איזה שרת רץ החדר, או מקצה חדר חדש → מחזיר כתובת Game Server ספציפי → הלקוח מתחבר ישירות (WebSocket) אליו לכל משך המשחק.

**כך "כולם משחקים עם כולם":** שחקן אינו קשור לשרת ספציפי. הפנייה לחדר תמיד עוברת דרך ה-Registry, כך שכל שחקן יכול להגיע לכל חדר, ללא תלות בשרת שאליו התחבר במקור.

## 3. עמידות, גיבויים ומקרי קצה

**נפילת Game Server בודד:**
Docker כזה מריץ אלפי חדרים בו-זמנית. אם קורס — **רק החדרים שהיו עליו נפגעים**, שאר המערכת ממשיכה כרגיל ("Blast Radius" מצומצם). הלקוחות המנותקים מזוהים ע"י ה-Gateway (Reconnect) ומנותבים למשחק/שרת חדש. הנזק מוגבל יחסית כי משחק בודד קצר (30–90 שניות).

**זיהוי נפילה — Health Checks:**
Gateway/Kubernetes שולחים בדיקות תקינות תקופתיות לכל Game Server. שרת שלא מגיב מסומן "לא זמין" ומופסק הניתוב אליו מיידית.

**נפילת DB:**
מידע קריטי חייב גיבוי: **Master + Replicas** — עותק ראשי לכתיבה, עותקים לקריאה/גיבוי. אם ה-Master נופל, אחד ה-Replicas מקודם אוטומטית (Failover).

**עומס CPU/זיכרון גבוה:**
Kubernetes/K3s מנטרים מדדים בזמן אמת. כשעומס עולה מעל סף — מופעל **Horizontal Autoscaling**: הקמת Pods נוספים אוטומטית, ולהפך בירידת עומס (חיסכון במשאבים).

**היגמרות מקום בדיסק:**
ניקוי/רוטציה אוטומטית של לוגים ישנים, והתראות (Alerting) כשתפוסת הדיסק חוצה סף (למשל 80%). בנוסף — כיוון שחדרי משחק כמעט ולא כותבים לדיסק המקומי (ראו סעיף 4), הסיכון מצטמצם מלכתחילה.

## 4. הסבר וצידוק ההצעה

**דרישה 1 — 100 מיליון משתמשים רשומים:** DB יחסי מאונדקס נכון מכיל בקלות את הנפח — אין צורך ב-Sharding כבר בשלב זה, רק ברפליקציה לצורך עמידות וקריאה מבוזרת.

**דרישה 2 — 10 מיליון משתמשים בו-זמנית:** שרת בודד מוגבל (מספר sockets, CPU, זיכרון, רוחב פס). הפתרון: ריבוי Game Servers, כאשר כל חדר חי במלואו על שרת אחד, וה-Registry/Matchmaking מנתבים כל שחקן לשרת הנכון — כך כל שני שחקנים יכולים לשחק יחד ולהיכנס לכל חדר, ללא תלות בשרת שאליו התחברו במקור.

**דרישה 3 — תעבורת רשת:**
- 10M שחקנים × 0.5 הודעות/שנייה (צעד כל 2 שניות) = **5,000,000 הודעות/שנייה** נכנסות
- בהנחת ~100 בייט להודעה (מומלץ Protobuf/FlatBuffers בינארי ולא JSON) → כ-500MB/שנייה ≈ **4 Gbps** תעבורה נכנסת בלבד
- **Fan-out**: כל צעד משודר לשאר שחקני החדר (בממוצע 5–10 שחקנים בחדר) — התעבורה היוצאת מוכפלת בהתאם ויכולה להגיע לעשרות Gbps
- ביחס לרשתות datacenter מודרניות זהו נפח סביר, אך משמעותי מספיק כדי לחייב: פרוטוקול קליל ובינארי (לא HTTP/JSON מלא), WebSocket/UDP ולא HTTP Polling, ופיזור גיאוגרפי (Multi-region deployment) לצמצום Latency ולפיזור עומס בין אזורים — רלוונטי כי המשתמשים "מכל העולם" (כלשון הדרישה המקורית)

**דרישה 4 — משך משחק קצר (30–90 שניות):**
- חדרים נפתחים ונסגרים בתדירות גבוהה מאוד — Game Server צריך לתמוך בפתיחה/סגירה מהירה של חדרים *בתוך* אותו תהליך (לא הקמת Container נפרד לכל משחק בודד — יקר ואיטי מדי ביחס למשך המשחק עצמו, ובקנה מידה של מיליוני חדרים במקביל בלתי ניתן לניהול).
- מצדיק אוטוסקיילינג אגרסיבי: K8s/K3s מעלים/מורידים Pods בתדירות גבוהה בהתאם לעומס הרגעי, בניגוד לשירותים "כבדים" ארוכי-טווח.
- הפרדה ברורה בין סוגי Docker-ים: Gateway/Matchmaking — ארוכי-חיים, Stateless; Game Instance — קצרי-חיים, "נוצרים לפי דרישה".
- Container של משחק לא זקוק ל-Disk Persistence כבד — בסיום המשחק, התוצאה הסופית נכתבת פעם אחת בלבד ל-DB הראשי (ולא לאורך כל המשחק).
- קיצור משך המשחק גם מקטין את "רדיוס הנזק" של נפילת שרת (ראו סעיף 3) — משחק שאבד הוא קצר וגורם נזק מוגבל לחוויית המשתמש.

**הנחת יסוד:** כל השרתים לעיל רצים כ-Processes בתוך Docker Containers, המתוזמרים ע"י Kubernetes/K3s — אחראים על Service Discovery, Health Checks, Auto-scaling אופקי, ו-Load Balancing בין ה-Game Servers.
